How Web Bot Auth works

Web Bot Auth is an IETF draft protocol that signs automated HTTP traffic with HTTP Message Signatures (RFC 9421). An agent's identity is its origin, such as https://buyer.wba-demo.noetis.dev. The agent publishes its public keys in a signed key directory at a fixed path on that origin, and signs each request with its private key.

A verifier reads the origin from the request, fetches that directory over HTTPS, and checks the signature. The TLS certificate for the host ties the keys to the domain, so the verifier needs nothing in advance: no key, no secret, no registration.

The four steps in Figure 1 work as follows:

  1. The buyer signs the request. Signature-Input lists what the signature covers: the method, the target URI, the authority, and Signature-Agent, which names the buyer's directory URL. With a body, Content-Digest carries the body's SHA-256, and the signature covers it too.
  2. The seller takes the host from Signature-Agent and fetches https://<host>/.well-known/http-message-signatures-directory. It follows no redirects, and it keeps the directory for up to 300 seconds.
  3. The directory is a JWK Set. Each key signs the directory response itself, and each key's kid is its JWK thumbprint.
  4. The seller selects the key by the pair of origin and keyid, verifies the signature and Content-Digest, checks the time window, and records the nonce, so the same request can't be replayed.

Responses work the same way. The seller signs each answer as its own origin, and that signature also covers the request's signature. The answer is bound to that exact request, so nobody can replay it as the answer to another one.

OpenProposal § 2.8 profiles these rules for agent traffic: Ed25519 keys, exactly one signature per message, a lifetime of at most 300 seconds, and 60 seconds of clock skew. It adds no header, tag, key field, or error code, so a standard Web Bot Auth implementation configured with these rules interoperates. Read the OpenProposal 3.0 specification and the Web Bot Auth library both agents use.

The identity boundary

A bearer token and a Web Bot Auth signature are both transport-level credentials. The seller handles them in one place, IdentityBoundary in seller/boundary.py. Every agent-facing route asks it for its caller and never reads a header itself.

The boundary takes four steps:

  1. Read. The boundary finds which credential the request presents. A request that presents both a signature and a token gets 400.
  2. Confirm. A signature goes to the library's RequestVerifier, which fetches the directory and checks Content-Digest against the body. A token is confirmed when its SHA-256 matches a stored row. The seller never stores the token itself.
  3. Resolve. The confirmed credential maps to the principal in the seller's own credentials table: by verified origin, or by token hash. A verified origin with no row is an established identity with no principal: a PublicCaller that carries the signature.
  4. Freeze. The boundary returns one immutable value, ResolvedCaller or PublicCaller. Nothing downstream can change it.

The offer logic is credential-blind. The boundary records only what it confirmed of the caller, as a provenance: the principal, the credential method, and, for a signature, the signed request and whether it covers the body. The offer logic receives only the principal, and an entry writer that holds the provenance, never the caller or its credential, so no offer decision depends on which credential the caller used. When it writes the buyer's entry, the writer decides whether the signature attributes it (§ 4.1.2) against the buyer the issued record names, not against the caller. The boundary writes nothing: the signed request is kept only with an entry it carried.

A credential that fails is refused at the boundary, before anything parses the body. The refusal is a transport status with no errors[] object:

Two credentials, one identity type

The same flow runs with either credential and reaches the same ResolvedCaller type, so you can add Web Bot Auth next to bearer tokens without touching the business logic. Both credentials point at the same principal: one buyer is one party, whichever credential it presents. The live run proves it every 15 minutes: the buyer reaches agreed with a signature and with a token, through the same code, and the seller resolves the same principal both times. The offer flow

The buyer reads a proposal the seller issued to it, and commits to one line item. The seller checks the commit and accepts. Each message is signed, and each answer is bound to the request it answers.

Each side does the following:

  • The seller shows an issued proposal only to its buyer. On a commit it recomputes record_digest over the line items plus the commit's writes, runs the checks of § 5.6.1, and writes the buyer's commitment entry and its own acceptance. A repeated commit with the same idempotency_key gets the stored result.
  • The buyer refuses an answer it can't verify: unsigned, unbound, bound to another request, or with a Content-Digest that doesn't match its body. It refuses an answer that verifies but doesn't parse, too. It re-sends the same Commit until an answer verifies, and then checks that the acceptance matches its commitment.
  • Both keep the counterparty's signed message as exact bytes, with the exact directory bytes it verified against. That evidence verifies again later, offline, which is what § 4.1.2 asks a party to be able to show.

One SDK on both sides

The buyer and the seller import the same generated OpenProposal SDK and the same Web Bot Auth library. Their business logic differs: one composes a commit, and the other checks it. Everything they must agree on is the same code.

An agreement holds only if both parties compute the same record_digest: the SHA-256 of the binding record in RFC 8785 canonical form. A party that parses one field differently, drops an unknown member, or writes a number another way computes a different digest, and the seller answers record_mismatch. The same holds for signatures: two verifiers that read the profile differently accept different messages.

A generated SDK removes that risk at the source. Every party, in every language, gets types generated from one schema, so each one parses and serializes the same way. The Web Bot Auth library does the same for signing and verification. When the buyer and the seller each use these packages, they agree by construction rather than by testing each pair.

Stopgap: protocol/ holds the rules the SDK generator doesn't emit yet: the binding record and record_digest, and the § 5.6.1 rules that tie a Commit's members together. It is typed on the generated classes, and both parties call it. When the generator emits these helpers, both parties import them from openproposal like every type.

The setup

The live deployment

One host runs the three agents as containers, each on a port that only the host can reach. Caddy terminates TLS with Let's Encrypt certificates and passes each public name to its agent. The agents trust public certificate authorities only, and they call each other by public name, through DNS and Caddy, like any outside party.

Try it

Each agent publishes its key directory at its own origin:

Seller

seller.wba-demo.noetis.dev/.well-known/http-message-signatures-directory

Buyer

buyer.wba-demo.noetis.dev/.well-known/http-message-signatures-directory

cfbot

cfbot.wba-demo.noetis.dev/.well-known/http-message-signatures-directory

Fetch a directory

The response is a JWK Set. Its Signature-Input and Signature headers sign the response once per key, with tag="http-message-signatures-directory":

curl -si https://buyer.wba-demo.noetis.dev/.well-known/http-message-signatures-directory

Call the seller without a credential

The seller answers 200 with a PublicCaller that has no credential. The answer itself is signed: look for Signature-Agent, Signature-Input, and Signature.

curl -si https://seller.wba-demo.noetis.dev/whoami
# {"kind":"public","signature":null}

Present a failing credential

A failing credential is refused, never treated as no credential. A token the seller didn't issue gets 401, and a signature without Signature-Agent gets 403 with an Accept-Signature header that says how to sign:

curl -si -H 'Authorization: Bearer not-a-token' https://seller.wba-demo.noetis.dev/whoami
# 401, WWW-Authenticate: Bearer error="invalid_token"

curl -si -H 'Signature-Input: sig1=("@method");tag="web-bot-auth"' \
     -H 'Signature: sig1=:AAAA:' https://seller.wba-demo.noetis.dev/whoami
# 403, {"error":"signature-agent-missing","detail":...}

Check a directory with Cloudflare's tools

Cloudflare Research publishes tools for Web Bot Auth that know nothing about this demo:

  • On the Cloudflare Research debug page, paste a directory URL into Validate key directory. To check a kid, paste a key from the directory into Get JWK keyid and compare the thumbprint.
  • Install the http-signature-directory command-line validator, and run it against a directory:
cargo install http-signature-directory
http-signature-directory https://buyer.wba-demo.noetis.dev/.well-known/http-message-signatures-directory

The demo also runs Cloudflare's library itself: on every run, cfbot verifies a request the buyer signs with web-bot-auth's verify(), after it checks the directory's own signatures. The verdict is the last step under Latest run.

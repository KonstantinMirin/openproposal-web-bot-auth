# Deploy the live demo

This directory runs the demo live at `https://wba-demo.noetis.dev` on one host
that already runs Caddy (hetzner2). It is separate from the local end-to-end
test in `e2e/`: real origins, Let's Encrypt certificates from the host's Caddy,
public roots only, and production cache and rotation values.

| File | What it is |
| :--- | :--- |
| `docker-compose.prod.yml` | The seller, the buyer, cfbot, and the runner. Agents listen on `127.0.0.1` only. |
| `Caddyfile.snippet` | The four site blocks to add to the host's `/etc/caddy/Caddyfile`. |
| `make-env.sh` | Writes the secrets file once, mode 600. |
| `localhost/` | A local rehearsal of this deployment (`make live-local`). Never deployed. |

## Host layout

The compose file finds everything relative to itself. The repository vendors
the library it builds with (`vendor/iab-agentic-primitives/`), so it is the one
checkout:

```text
/srv/wba-demo/
├── openproposal-web-bot-auth/   this repository
├── wba-demo.env                 the secrets (make-env.sh), mode 600
└── run/                         latest-run.json and history.json; the runner writes, Caddy reads
```

The checkout holds no state: keys and SQLite databases live in Docker volumes,
and secrets and reports live outside it.

## Settings

The secrets file holds four values, all generated by `make-env.sh`. Every
`docker compose` command passes it with `--env-file`, and the compose files give
each service only the values it names:

| Variable | Used by | Purpose |
| :--- | :--- | :--- |
| `SELLER_OPERATOR_KEY` | Seller (as `OPERATOR_KEY`), runner | The seller's own controls (`/operator/`) require it in `X-Operator-Key`. |
| `BUYER_OPERATOR_KEY` | Buyer (as `OPERATOR_KEY`), runner | The buyer's own controls (`/operator/`) require it. |
| `CFBOT_OPERATOR_KEY` | cfbot (as `OPERATOR_KEY`) | cfbot's own controls (`/run/`) require it. The runner never calls them. |
| `DEMO_BEARER_TOKEN` | Seller, buyer, runner | The token the seller issues its buyer, beside the buyer's origin: two credentials of one principal. The seller stores only its SHA-256. |

Each party's key is its own, so one party's key opens no other party's controls.

You can override these Compose variables when you run `docker compose`:

| Variable | Default | Purpose |
| :--- | :--- | :--- |
| `WBA_RUN_DIR` | `../../run` | Where the runner writes its reports |
| `RUN_INTERVAL` | `900` | Seconds between runs |

### Every environment variable

Each service reads its environment once, in its settings module
(`seller/settings.py` and `buyer/settings.py`, on the variables both agents
share in `shared/settings.py`; `runner/settings.py`; `e2e/scenarios/stack.py`) or at the top of `cfbot/server.mjs`. The
default is what the service uses when the variable is unset; the compose files
set the values the table's last column names.

| Variable | Service | Default | What it sets |
| :--- | :--- | :--- | :--- |
| `SELF_ORIGIN` | Seller, buyer, cfbot | `https://<service>.wba-demo.noetis.dev` | The service's own origin, which it signs as and verifies against |
| `SELF_LEGAL_NAME` | Seller, buyer | `Demo Seller Inc.`, `Demo Buyer Agency LLC` | The legal name the agent trades under, beside its own origin's host: the seller issues every proposal under it, and the buyer takes only proposals that name its host as the buyer's domain |
| `PEER_SELLER_LEGAL_NAME` | Buyer | `Demo Seller Inc.` | The seller's legal name, as the buyer names it |
| `PEER_BUYER_LEGAL_NAME` | Seller | `Demo Buyer Agency LLC` | The buyer's legal name, as the seller records its principal |
| `PEER_BUYER_ORIGIN` | Seller, runner, scenarios | `https://buyer.wba-demo.noetis.dev` | The buyer's origin, whose host is its domain: the seller records its one principal from it once, and refuses to start if a later boot names another; the buyer the runner and the scenarios check |
| `PEER_SELLER_ORIGIN` | Buyer, cfbot, runner, scenarios | `https://seller.wba-demo.noetis.dev` | The seller the buyer deals with and cfbot calls |
| `PEER_CFBOT_ORIGIN` | Buyer, runner, scenarios | `https://cfbot.wba-demo.noetis.dev` | Cloudflare's verifier |
| `DATA_DIR` | Seller, buyer | `/data` | The database (`seller.db`, `buyer.db`), on the `-db` volume |
| `KEYS_DIR` | Seller, buyer | `/keys` | The signing key (seller `wba-key.jwk`) or keyring (buyer), on the `-keys` volume |
| `CFBOT_KEY` | cfbot | `/data/cfbot-key.jwk` | cfbot's signing key, on `cfbot-data` |
| `SSL_CERT_FILE` | Seller, buyer, runner, scenarios | The system's roots | The trust store for every outgoing call; unset live, the throwaway CA bundle locally |
| `NODE_EXTRA_CA_CERTS` | cfbot | None | The throwaway CA, locally only |
| `OPERATOR_KEY` | Seller, buyer, cfbot | None: every control call is refused | What `X-Operator-Key` must carry: the agent's own key, from the secrets file |
| `SELLER_OPERATOR_KEY`, `BUYER_OPERATOR_KEY` | Runner, scenarios | None: required, so the runner won't start | Each agent's own key, sent to that agent's controls only |
| `CFBOT_OPERATOR_KEY` | Scenarios | None: required | cfbot's own key, for its `/run/` controls |
| `DEMO_BEARER_TOKEN` | Seller, buyer, runner, scenarios | None: no bearer credential | The token the seller issues its buyer; the runner reads it only to keep it out of reports |
| `WBA_DIRECTORY_MAX_AGE` | Seller, buyer, scenarios | `300` | The directory's `Cache-Control: max-age` (the e2e buyer: `0`). A buyer key waits this plus 300 s before it signs |
| `WBA_MAX_CACHE_AGE` | Seller, buyer, scenarios | The library's, `300` | How long a cached directory answers without a fetch (the e2e seller: `20`) |
| `WBA_SIGNATURE_LIFETIME` | Buyer, scenarios | `300` | How long the buyer's request signatures last, 1 to 300 s (e2e: `10`) |
| `DEMO_FAULT_INJECTION` | Seller | Off | TEST ONLY: mounts `PUT /test/fault`; `make live-config` keeps it out of production |
| `SELLER_CONTROL`, `BUYER_CONTROL` | Runner, scenarios | `http://seller:8000`, `http://buyer:8000` | The agents' own controls, inside the network |
| `CFBOT_CONTROL` | Scenarios | `http://cfbot:8000` | cfbot's own controls, inside the network |
| `SELLER_DB`, `BUYER_DB` | Runner, scenarios | `/seller-data/seller.db`, `/buyer-data/buyer.db` | Both parties' databases, mounted read-only from the `-db` volumes |
| `BUYER_KEYS_DIR` | Scenarios | `/buyer-keys` | The buyer's key directory, mounted read-only |
| `OUT_DIR` | Runner | `/out` | Where the reports go |
| `RUN_INTERVAL` | Runner | `900` | Seconds between runs; `0` runs once |

`docker-compose.prod.yml` fixes everything else: the three origins
`https://seller.wba-demo.noetis.dev`, `https://buyer.wba-demo.noetis.dev`, and
`https://cfbot.wba-demo.noetis.dev`; a directory `Cache-Control: max-age` of
300 s, from which the buyer derives a rotation wait of 600 s; a verifier
`max_cache_age` of 300 s; and a signature lifetime of 300 s. No service sets `SSL_CERT_FILE` or
`NODE_EXTRA_CA_CERTS`, so the agents trust the image's public roots only, and
the seller's test-only fault toggle isn't mounted.

## Deploy

Run these steps in order. The host is `hetzner2`, and the commands that start
with `rsync` run on your laptop from the directory that holds the checkout.

1.  Check that no placeholder is left in the tree: run `make placeholders`,
    which CI runs too. It fails on any placeholder outside the seed template
    `seller/seed/proposal.yaml`, whose placeholders the seller fills in when it
    issues a proposal.

2.  In Route 53, in the `noetis.dev` hosted zone, create four `A` records with
    a TTL of 300, each pointing at the host's public IPv4 address. On
    2026-11-07, `salesagent.noetis.dev` resolved to that address,
    `167.235.98.225`:

    | Name | Type | Value |
    | :--- | :--- | :--- |
    | `wba-demo.noetis.dev` | `A` | `167.235.98.225` |
    | `seller.wba-demo.noetis.dev` | `A` | `167.235.98.225` |
    | `buyer.wba-demo.noetis.dev` | `A` | `167.235.98.225` |
    | `cfbot.wba-demo.noetis.dev` | `A` | `167.235.98.225` |

    Add `AAAA` records only if the host's Caddy listens on IPv6. To confirm the
    records, run `dig +short A seller.wba-demo.noetis.dev`.

3.  Copy the checkout to the host:

    ```bash
    ssh hetzner2 'mkdir -p /srv/wba-demo'
    rsync -av --delete --exclude .git --exclude .venv --exclude __pycache__ \
        --exclude .pytest_cache --exclude .ruff_cache --exclude node_modules \
        --exclude e2e/generated --exclude deploy/localhost/generated \
        openproposal-web-bot-auth/ hetzner2:/srv/wba-demo/openproposal-web-bot-auth/
    ```

    `--delete` is safe here: the checkout holds no secrets, keys, or reports.

4.  On the host, write the secrets and create the report directory. The runner
    runs as UID 10001, and Caddy reads the files it writes:

    ```bash
    /srv/wba-demo/openproposal-web-bot-auth/deploy/make-env.sh
    install -d -o 10001 -g 10001 -m 755 /srv/wba-demo/run
    ```

5.  On the host, build and start the three agents:

    ```bash
    cd /srv/wba-demo/openproposal-web-bot-auth
    docker compose --env-file ../wba-demo.env -f deploy/docker-compose.prod.yml up --detach --build --wait seller buyer cfbot
    ```

6.  On the host, append the snippet to the Caddyfile, validate it, and reload
    Caddy. Caddy gets the four certificates from Let's Encrypt, which needs the
    DNS records from step 2:

    ```bash
    cat /srv/wba-demo/openproposal-web-bot-auth/deploy/Caddyfile.snippet >> /etc/caddy/Caddyfile
    caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
    systemctl reload caddy
    ```

7.  On the host, start the runner. It runs the flow at once, and then every
    15 minutes:

    ```bash
    docker compose --env-file ../wba-demo.env -f deploy/docker-compose.prod.yml up --detach runner
    docker compose --env-file ../wba-demo.env -f deploy/docker-compose.prod.yml logs runner
    ```

    The log line of a good run reads `<time> pass <ms> ms`.

8.  Check the deployment from your laptop:

    ```bash
    curl -si https://buyer.wba-demo.noetis.dev/.well-known/http-message-signatures-directory
    curl -s https://wba-demo.noetis.dev/latest-run.json | python3 -c 'import json,sys; print(json.load(sys.stdin)["ok"])'
    curl -s -o /dev/null -w '%{http_code}\n' -X POST https://buyer.wba-demo.noetis.dev/operator/keys   # 404
    ```

    Open `https://wba-demo.noetis.dev` and check that **Latest run** shows
    **Pass**.

## Update

Repeat step 3, and then rebuild and restart every service on the host:

```bash
docker compose --env-file ../wba-demo.env -f deploy/docker-compose.prod.yml up --detach --build --wait
```

Keys and databases persist across rebuilds, each agent's in two volumes:
`wba-demo-live_seller-keys` and `wba-demo-live_seller-db`, and
`wba-demo-live_buyer-keys` and `wba-demo-live_buyer-db`. The runner mounts the
two `-db` volumes read-only and neither `-keys` volume, so it can read no
agent's key. To change only the site, repeat step 3; Caddy serves the files
directly.

### Move to the split volumes, once

A deployment from before the split keeps each agent's key and database in one
volume, `wba-demo-live_seller-data` or `wba-demo-live_buyer-data`, which the
runner mounted. To keep the keys and the records, move each file into its own
volume before the first `up` of the new compose file. On the host:

```bash
cd /srv/wba-demo/openproposal-web-bot-auth
docker compose --env-file ../wba-demo.env -f deploy/docker-compose.prod.yml down
docker compose --env-file ../wba-demo.env -f deploy/docker-compose.prod.yml create   # creates the four new volumes
docker run --rm -v wba-demo-live_seller-data:/old -v wba-demo-live_seller-keys:/keys \
    -v wba-demo-live_seller-db:/data alpine sh -c \
    'mv /old/wba-key.jwk /keys/ && mv /old/seller.db /data/ && chown -R 10001:10001 /keys /data'
docker run --rm -v wba-demo-live_buyer-data:/old -v wba-demo-live_buyer-keys:/keys \
    -v wba-demo-live_buyer-db:/data alpine sh -c \
    'mv /old/keys/* /keys/ && mv /old/buyer.db /data/ && chown -R 10001:10001 /keys /data'
docker volume rm wba-demo-live_seller-data wba-demo-live_buyer-data
docker compose --env-file ../wba-demo.env -f deploy/docker-compose.prod.yml up --detach --build --wait
```

Then check that the runner can't read a key, and that its next run passes:

```bash
docker compose --env-file ../wba-demo.env -f deploy/docker-compose.prod.yml run --rm --no-deps --entrypoint sh runner \
    -c 'find / -path /proc -prune -o -name "*.jwk" -print'   # prints nothing
docker compose --env-file ../wba-demo.env -f deploy/docker-compose.prod.yml logs runner
```

## Operate

- **Growth.** Each run issues two proposals and keeps their records and
  evidence: about 50 KB across both databases, or about 5 MB a day. To start
  over, run `down --volumes` as in [Tear down](#tear-down), and then step 5 and
  step 7. The agents mint new keys on the next start.
- **Firewall.** The agents and the runner reach each other's public names from
  inside Docker, so packets from the Docker bridge reach the host's public
  address on port 443. If a host firewall drops them, the directory steps fail
  with a connection error. Allow port 443 from the Docker bridge networks.
- **Rotate the buyer's key.** The keyring enforces production waits. On the
  host, with the buyer's own key, `BUYER_OPERATOR_KEY`, from
  `/srv/wba-demo/wba-demo.env`:

  ```bash
  key=$(sed -n 's/^BUYER_OPERATOR_KEY=//p' /srv/wba-demo/wba-demo.env)
  curl -s -H "X-Operator-Key: $key" -X POST http://127.0.0.1:18082/operator/keys   # publish
  # 600 s later:
  curl -s -H "X-Operator-Key: $key" -X POST http://127.0.0.1:18082/operator/keys/NEW_KID/activate
  # 300 s after that:
  curl -s -H "X-Operator-Key: $key" -X DELETE http://127.0.0.1:18082/operator/keys/OLD_KID
  ```

## Rehearse locally

To run this compose file on a laptop, run `make live-local`. The override in
`localhost/` adds what stands in for public DNS and Let's Encrypt: a Caddy
container that serves `Caddyfile.snippet` with its upstreams pointed at the
containers, network aliases for the four names, and the e2e stack's throwaway
CA. The script runs the runner once and checks that the site serves a passing
`latest-run.json`, doesn't route the operator controls, and that no `*.jwk`
file is readable in the runner's container. With `KEEP=1`, the stack stays up.

To validate the compose file alone, run `make live-config`.

## Tear down

The following steps remove the deployment. Steps 1 and 4 delete the agents'
keys, databases, secrets, and reports permanently.

1.  On the host, stop the stack and delete its volumes and images:

    ```bash
    cd /srv/wba-demo/openproposal-web-bot-auth
    docker compose --env-file ../wba-demo.env -f deploy/docker-compose.prod.yml down --volumes --rmi all
    ```

2.  On the host, delete the four site blocks of the snippet from
    `/etc/caddy/Caddyfile`, and then run `caddy validate --config
    /etc/caddy/Caddyfile --adapter caddyfile` and `systemctl reload caddy`.

3.  In Route 53, delete the four `A` records.

4.  On the host, delete the files: `rm -r /srv/wba-demo` and
    `rm /var/log/caddy/wba-demo-access.log*`.
